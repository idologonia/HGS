# 11. План реалізації та тестування

Кожен етап закінчується тестами. Функція вважається готовою **лише після фактичної перевірки**.
У таблицях позначено, де перевіряти: 🐧 — можна в будь-якому середовищі (автотести), 🪟 — потрібен Windows
(GitHub Actions `windows-latest` та/або ваш ПК), 🌐 — потрібен реальний інтернет-доступ / інший пристрій.

## Етап 1 — Архітектура ✅ (цей комплект документів)

Результат: `docs/architecture/01–12`. Чекає на погодження.

## Етап 2 — Мінімальне робоче ядро

| Задача | Деталі |
|--------|--------|
| Каркас проєкту | `pyproject.toml`, зафіксовані версії, `__main__` з режимами GUI/core |
| Ядро | Event Bus, Logger, Database Manager + міграція v1, settings.json, single-instance |
| Admin API | `/status`, `/games` (CRUD), `/events` WS, токен, перевірка Host/Origin |
| Gateway | `/hgs/v1/ws` з `hello` (режим `open` + `invite`), ping/pong, ліміти розміру/частоти, `/health` |
| Адаптери | `BaseAdapter`, `AdapterRegistry`, `html`-адаптер у режимі `relay` |
| Кімнати/сесії | Room/Session/Player Manager (без resume) |
| GUI | вікно, темна тема, Dashboard (реальні метрики), Games (картки, Start/Stop/Restart, додавання гри), Logs |
| Windows CI | GitHub Actions: тести + запуск ядра на windows-latest |

Тести: 🐧 протокол і ліміти (unit); 🐧 ядро + 2 WS-клієнти в одній кімнаті; 🐧 GUI smoke (offscreen);
🪟 запуск і зупинка на Windows.

## Етап 3 — Перша тестова гра

* `examples/demo-arena`: HTML-сторінка, кожен гравець — кружечок, позиції синхронізуються.
  Варіант A — `relay`; варіант B — `logic` (серверний `on_tick`), щоб перевірити обидва шляхи.
* `hgs.js` v1 (повний API з розділу 09, крім resume) + `hgs_sdk` (GameLogic, runner) + Worker Bus.
* Логіка запускається у воркері під Process Supervisor (Job Object на Windows).

Тести: 🐧 два headless-браузери (Playwright) бачать рухи один одного; 🐧 дві кімнати не бачать подій одна
одної; 🐧 дві різні ігри ізольовані; 🐧 падіння воркера (`os._exit`) не зачіпає ядро й іншу гру, спрацьовує
політика перезапуску і стан `FAILED`; 🐧 GUI не блокується при 100 повідомленнях/с.

## Етап 4 — Інтернет

* Network Manager: режими local/lan/direct/tunnel, перемикання без зміни адаптерів.
* Cloudflare Quick Tunnel (запуск `cloudflared`, парсинг URL, нагляд), потім Named Tunnel.
* Direct: TLS із файлів сертифіката; DuckDNS-оновлювач; (опційно) Let's Encrypt DNS-01.
* Auth: invite/password/account, player_token, resume_token з ротацією, `seq`, блокування IP, security.log,
  allowed_origins, `CF-Connecting-IP`.
* Network-вкладка, діагностика CGNAT, перевірка досяжності, посилання-запрошення з QR.

Тести: 🐧 безпека (підбір, повтор resume_token, завеликі/зіпсовані кадри, флуд, чужий Origin);
🌐 демо-гра з GitHub Pages через тунель — підключення з телефону через мобільний інтернет (HTTPS/WSS);
🌐 розрив інтернету на клієнті → resume у ту ж кімнату.

## Етап 5 — Python Adapter

* `python`-адаптер: `worker` і `standalone`, вибір інтерпретатора/venv, allowlist, stdout/stderr у логи,
  PID/uptime/код виходу, ліміти Job Object, перевірка готовності.
* Проксі Gateway → standalone-сервер.
* `process`-адаптер + приклад на Node.js.

Тести: 🐧/🪟 старт/стоп/рестарт, зависання (немає heartbeat), спроба вказати точку входу поза директорією гри,
коректне завершення дерева процесів; 🪟 Job Object вбиває воркери при аварійному вбивстві ядра.

## Етап 6 — Розширення GUI

Players (kick/ban/токени), Rooms (створення/закриття/ліміти), Settings гри з JSON-схеми, ресурси по іграх,
Saves (знімки, бекапи, відновлення), Invite-діалог, трей.

Тести: 🐧 GUI-тести дій; ручна перевірка сценаріїв з розділу 17 ТЗ.

## Етап 7 — Надійність

Систематична перевірка: аварійні завершення (ядро, воркер, cloudflared), втрата інтернету, перепідключення,
пошкоджені повідомлення (fuzz-тест протоколу), Stop під час активної гри (збереження + повідомлення гравцям),
одночасна робота 3+ ігор, тривалий прогін (soak-тест 2–4 год) з контролем пам'яті, вимкнення Windows
(`WM_QUERYENDSESSION`).

## Етап 8 — Збірка

PyInstaller `--onedir`, іконка, версія у файлі, інсталятор (Inno Setup — безкоштовний) або zip-портативна
версія, збірка в GitHub Actions, інструкції `docs/guides/*`. Перевірка на «чистій» Windows 10/11 без Python.

## Обмеження середовища розробки

Розробка відбувається в Linux-контейнері. Усе, що залежить від Windows (Job Objects, DPAPI, PyInstaller-збірка,
поведінка брандмауера, вимкнення ПК), буде перевірятися через GitHub Actions `windows-latest`
(безкоштовно для публічних репозиторіїв; для приватних — у межах безкоштовних хвилин) та фінально — на вашому ПК.
Такі пункти не позначатимуться готовими без цієї перевірки.
