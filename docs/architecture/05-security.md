# 05. Безпека

## 5.1. Модель загроз (що захищаємо і від кого)

| Загроза | Захист |
|---------|--------|
| Хтось з інтернету керує HGS | Admin API лише на `127.0.0.1`, окремий порт і застосунок, токен на кожен запуск, перевірка `Host`/`Origin` |
| Виконання команд Windows через мережу | Немає жодного шляху «повідомлення → команда». Процеси запускаються лише з конфігу гри, який редагує власник у GUI. Allowlist інтерпретаторів і директорій |
| Чужий сайт підключає браузер жертви до сервера | Список дозволених `Origin` для кожної гри (наприклад, `https://user.github.io`) |
| Підбір паролів/кодів | Ліміт спроб, затримка, тимчасове блокування IP, логування |
| Крадіжка/повтор токена | Токени — лише в хешованому вигляді в БД; одноразові `resume_token` з ротацією; `seq` у повідомленнях; токени не передаються в URL |
| Флуд і великі пакети | Ліміт розміру кадру, token bucket на сесію і на IP, ліміт з'єднань на IP |
| Пошкоджені пакети | Строга pydantic-схема конверта, некоректний JSON → помилка і лічильник; N помилок → розрив |
| Гра A читає дані гри B | Окремі процеси, окремі директорії, контекст адаптера обмежений своєю грою, Router перевіряє `game_id` |
| Шкідливий/забагований код гри | Процес-воркер зі звичайними правами, Job Object з лімітами; гра не бачить токенів/БД ядра |
| Витік секретів у логах | Фільтр маскування токенів і паролів |

Чесне обмеження: код ігор і плагінів, які власник сам додав, — довірений. HGS не є пісочницею для чужого
недовіреного коду; ізоляція процесів захищає від помилок, а не від навмисно шкідливої програми.

## 5.2. Вхід гравців

Режим задається для кожної гри (`auth.mode`):

| Режим | Як працює | Коли |
|-------|-----------|------|
| `invite` *(типово)* | Власник створює код запрошення в GUI (термін дії, кількість використань, опційно кімната). Гравець вводить ім'я + код → отримує **токен гравця** | гра з друзями |
| `password` | Спільний пароль гри (scrypt-хеш) + ім'я | простий варіант |
| `account` | Реєстрація ім'я + пароль у межах гри (scrypt) | ігри з прогресом гравця |
| `open` | Лише ім'я, без перевірки. Дозволено тільки в мережевому режимі `local`/`lan`, GUI не дасть увімкнути разом із тунелем/Direct | тести |

Глобального акаунта для всіх ігор немає (вимога 7): гравець прив'язаний до `game_id`.

## 5.3. Токени

| Токен | Довжина | Зберігання на сервері | Термін | Призначення |
|-------|---------|-----------------------|--------|-------------|
| `invite_code` | 10 символів (base32, без схожих літер) | SHA-256 | до 7 днів / N використань | одноразовий вхід |
| `player_token` | 32 байти (`token_urlsafe`) | SHA-256 | 30 днів, ковзний; відкликається | повторний вхід з того ж браузера (зберігається в `localStorage`) |
| `session_id` | 16 байт | у пам'яті | поки жива сесія | ідентифікатор з'єднання |
| `resume_token` | 32 байти | у пам'яті, хеш | **одноразовий**, 30 с після розриву | повернення після розриву; після використання видається новий |
| `admin_token` | 32 байти | у пам'яті | один запуск HGS | GUI → Admin API |
| `worker_token` | 32 байти | у пам'яті, хеш | один запуск воркера, одне підключення | воркер → Worker Bus |

Порівняння токенів — `hmac.compare_digest`. Токени передаються лише в тілі першого WS-повідомлення
(не в URL, бо URL потрапляють у логи проксі/тунелів).

## 5.4. Ліміти (типові, налаштовуються для кожної гри)

| Параметр | Значення |
|----------|----------|
| Розмір WS-кадру | 16 КБ (макс. 1 МБ) |
| Частота повідомлень | 30/с, сплеск 60 (token bucket) |
| Таймаут `hello` після відкриття сокета | 5 с |
| З'єднань з однієї IP | 8 |
| Спроб входу | 5 за хвилину на IP → блок 5 хв; 20 за годину → блок 1 год |
| Некоректних повідомлень | 10 поспіль → розрив з'єднання + запис у security.log |
| `room_state` (relay) | 64 КБ |

За тунелем Cloudflare справжня IP гравця береться з заголовка `CF-Connecting-IP` **лише** якщо з'єднання
прийшло від локального `cloudflared` (127.0.0.1) — інакше заголовок ігнорується (його можна підробити).

## 5.5. Секрети

* Токени тунелю, DuckDNS, пароль ключа TLS → шифруються **Windows DPAPI** (прив'язка до облікового запису
  Windows) і зберігаються в таблиці `secrets`.
* Паролі гравців → `hashlib.scrypt` (n=2^15, r=8, p=1, сіль 16 байт).
* Файли даних — у `%LOCALAPPDATA%\HGS` (доступний лише поточному користувачу Windows).

## 5.6. Журнал підозрілих подій (`logs/security.log` + таблиця `security_events`)

Невдалі входи, блокування IP, перевищення лімітів, некоректні пакети, невідомий `Origin`, повторне використання
`resume_token`, спроба воркера адресувати чужу гру. Подія `security.alert` з'являється в GUI.

## 5.7. Запуск процесів

* Без `shell=True`, лише `create_subprocess_exec` зі списком аргументів.
* Інтерпретатор має бути в allowlist (автоматично: Python, вбудований у HGS; `venv` усередині директорії гри;
  вручну доданий власником шлях — з підтвердженням).
* Точка входу і робоча директорія — всередині зареєстрованої директорії гри (перевірка `realpath`).
* Змінні середовища воркера: мінімальний набір + `HGS_WORKER_URL`, `HGS_WORKER_TOKEN`, `HGS_GAME_ID`,
  `HGS_DATA_DIR`. Секрети ядра не передаються.
* HGS працює без прав адміністратора і попереджає, якщо його запущено «від імені адміністратора».
